# EXP-027 · rr_proxy 开销拆分：replica2 的 1.63× 缺口里有多少是代理

> **一句话结论**：**判定 B——rr_proxy 的开销约 2%，在噪声内（阈值 5%），replica2 的 1.63× 缺口不来自代理**。两臂并发形态对齐（A = 两个直连客户端**同时**各打一个实例、各 600 请求 / conc64；B = 一个客户端经代理 1200 请求 / conc128）后：直连合计 **22.280 req/s**（A1 11.140 + A2 11.253，墙钟 53.9/53.3s）vs 经代理 **21.820**（复测 **21.862**，两次差 0.2%）→ 代理开销 **R = 2.06%（保守口径）/ 2.56%（乐观口径）**，两次 B 臂都稳定落在 2% 附近。**结论：1.63× 的剩余缺口必须去别处找**——按本实验的排除法，最可能是"两实例共享主机资源（CPU 调度 / PCIe / 内存带宽）"这一层，而不是转发层；rr_proxy 作为这一族方案的下限是**成立的**（它只贵 2%）。

## 1. 目的与假设

EXP-025 把 replica2@512 推到 25.30 req/s（conc256）仍未见平台，而 512 桶扩展效率只有 1.63×（replica2/colocate @conc128）。两处推断都指向同一个未拆分的变量：**`rr_proxy.py` 是单进程 uvicorn，逐请求转发且不做会话亲和**，它在 128 路流式并发下的开销从未被单独量过。

**假设（可证伪）**：replica2 的吞吐缺口（1.63× 而非 2×）有**可测的一部分**来自 rr_proxy。

**实验设计（关键：直连侧必须并发）**——要分离"代理开销"，两臂的**并发形态必须一致**，否则差里会混进"两实例同时跑 vs 单实例跑"的干扰：

| 臂 | 形态 | 客户端 | 总请求 | 每实例并发 |
|---|---|---|---|---|
| **A 直连（对照）** | 两个 benchmark 进程**同时**跑，各打自己那个实例 | 2 个 `vllm bench` 进程 | 600 + 600 = 1200 | 64 |
| **B 经代理** | 一个 benchmark 打到 rr_proxy，由代理轮询分发 | 1 个进程 | 1200 | 64（1200 请求 / 2 实例 / 128 代理并发 = 每实例约 64 在飞） |

这样两臂都是"两实例并发、每实例约 64 路在飞、总量 1200 请求、512×128"，**唯一变量是中间那层代理**。

**跑前锁定的判定阈值（跑完不改）**：

- 口径：`A_agg = 1200 / max(wall_A1, wall_A2)`（保守：按较慢的那个算，避免用"速率之和"高估直连臂）；`B = 1200 / wall_B`。
- **代理开销比 `R = (A_agg − B) / A_agg`**。
- **判定 A（代理有可测开销）**：`R ≥ 5%` → 代理开销成立，量化为 R，并从 1.63× 缺口里扣除这一份；同时记录 A 臂"速率之和"作为乐观上界。
- **判定 B（代理开销在噪声内）**：`R < 5%` → 缺口不来自代理，1.63× 的剩余部分归因于"两实例共享主机资源（CPU/PCIe/内存带宽）"+ SLO/公平性，而不是代理转发。
- 每臂要求：`failed_requests == 0`、gate 通过（经代理臂还要看代理日志无 5xx）；**三臂都在 fresh 栈上跑**，起栈后复核 `prefix_cache_hits_total` 增量 == 0。
- 两臂各跑一次（与 EXP-007/023 每点单次同规格）；**若 |R| < 5%（判定 B）则再复跑一次 B 臂**，确认不是单次抖动。
- 时间盒 ≤30 分钟。

## 6. 分析与结论

**【实测】① rr_proxy 的转发开销 ≈ 2%，不是 1.63× 缺口的主因。** 两臂并发形态对齐（都是两实例并发、每实例 ~64 路在飞、总量 1200）后，差值只有 2% 量级，而且两次 B 臂自身差 0.19%——**这个 2% 甚至在判定阈值（5%）之内，只能算"有微弱代价"**。

**【实测】② 直连臂的两实例几乎完全对称**：11.140 vs 11.253 req/s（差 1.0%），TTFT p50 593.9 vs 587.5 ms、TPOT p50 39.07 vs 38.57 ms。说明两个实例的硬件条件与负载分配是均衡的，A 臂作为对照是干净的。

**【实测】③ 经代理臂的 TTFT 明显更低（388 vs 594 ms），TPOT 略高（41.0 vs 38.8 ms）。** 机制：代理侧并发 128 > 直连侧每实例 64，请求在**客户端/代理这一层**排得更浅、更快进入引擎（TTFT 低），但每个实例内部同时在处理的请求更多、decode 互相挤（TPOT 高）。这与 EXP-025 的取向一致（并发越高 TPOT 越差）。

**【推断】④ 那 1.63× 的缺口在哪？本实验用排除法把它从代理层移开了。** 剩下的候选，按可能性排序：
1. **两实例共享主机资源**（未测）：两个 vLLM 进程在同机跑，prefill 阶段争 CPU 调度与 PCIe/内存带宽；本实验的 A 臂**也**是这个形态，所以两臂同受此影响——它解释了"为什么 2 个实例拿不到 2× colocate"，但不解释 A 与 B 的差；
2. **colocate 基线本身的口径**：1.63× 的分母是 colocate@512 conc128 = 12.81（EXP-023），而**单实例 colocate 的 conc128 是过饱和态**（TPOT p50 67 ms 已破 SLO、TTFT p90 4.6 s）。即分母站在"单实例已经很勉强"的位置上，2× 本就不该期望；
3. `rr_proxy` 不做会话亲和、也不看缓存命中（EXP-003 的教训），在真实生产路由下会进一步拉低——但那是**另一个方向**的损失，不在这 1.63× 里。

**【结论】**：`rr_proxy.py` 作为"这一族方案的下限"这一措辞是**站得住的**——它的转发代价只有 2%；把 1.63× 归因给代理是错的。要解释 2× 变 1.63×，下一步应测候选 1（两实例共享主机资源），做法是在**单实例**上把并发推到与双实例合计相同的总在飞量，看单实例能否复现 22.28 req/s。

## 7. 异常、偏差与开放问题

- **协议偏离（一处，已登记）**：A 臂的两个直连客户端用了**不同 seed**（1099 / 2099）——目的是避免两半请求的 prompt 完全相同（同一份 seed 会生成同一批 prompt）。这使 A 臂的 prompt 集合与 B 臂（单一 seed 1099、1200 条）并非逐条一致。**影响**：本题比的是吞吐而非逐请求延迟，且 512×128 的定长 workload 下 prompt 内容不影响计算量，故判定不受影响；但严格逐条可比性有所损失，如实登记。
- **`bc` 未安装**：脚本首跑的墙钟打印报 `bc: command not found`（不影响测量，A 臂墙钟由 bench JSON 的 `duration` 恢复）。已改为 shell 算术，复跑时正常。
- **每臂单次**：A 臂单次、B 臂两次（按预注册，判定 B 触发复跑）。A 臂未复跑——若要把 R 引用到 ±1% 精度需补，当前 2% 量级已足以支持"判定 B"。
- **未测（明确挂账）**：① 上文的候选 1（两实例共享主机资源的定量拆分：单实例总在飞量对齐实验）；② 代理侧的开销构成未拆（uvicorn 单进程 vs 多 worker、`httpx` 连接池、流式转发的拷贝次数）；③ 更高并发下代理是否先成为瓶颈（本次只到 conc128，EXP-025 已把 replica2 推到 conc256 但**未同时量代理侧 CPU**）；④ 会话亲和 / cache-aware 路由（属生产形态，不是本实验的下限口径）。
- 无 OOM、无端口冲突、无 5xx（代理日志实查无错误关键字）；时间盒实际约 6 分钟（起栈 ~70 s + A 臂 ~54 s + B 臂两次 ~110 s）。

## 8. 下游影响

- **EXP-023/024/025 的措辞可加强**：`rr_proxy` 的转发代价已实测 ≈2%，"replica2 数字是这一族方案的下限"这一说法可以补上"下限与上限的差不在转发层"。
- **1.63× 的归因需改写**：EXP-024 §6⑥ 把"rr_proxy 单进程转发开销"与"replica2 未封顶"并列为两个候选——**本实验排除前者**，只剩后者与"两实例共享主机资源"。`docs/TECH_DOC_vllm_engineering.md` 的 C11（"剩余缺口：conc128 下 TPOT 仍 <SLO 未封顶；rr_proxy 开销未拆分"）应更新为"未封顶 + 代理开销已测 ≈2%，缺口不在转发层"。
- **面试可用**：这是"用排除法把一个候选变量从归因里划掉"的一个完整例子，且带复跑自证（两次 B 臂差 0.19%）。
- **红线**：本实验不进 `runs.jsonl`、不进 fig1–7；2% 这个数只在"代理转发开销"这个语境下引用，不得与四臂吞吐数字混用。
