## 1. 目的与假设

## 6. 分析与结论

**【实测】① 装置校验近乎完美**：S1 = 11.135 vs A1 = 11.140，差 **0.04%**。这同时说明一件重要的事——**"第二个实例在不在跑"不改变第一个实例的吞吐**（S1 时 8200 也在跑，与 A1 环境相同；而 S1 与 S3 只差请求量，分别是 11.135 与 11.103，差 0.3%）。所以用 S 臂去对照 A 臂是干净的。

**【实测】② H-B 成立**：单实例在同样的 N=1200 下只能给 13.049，而两实例合计给 22.392 → **1.716×**。所以第二张卡**确有贡献**，H-A（"单实例即可承载"）被否。

**【实测·核心】③ 但"1.63×"是口径不对称的产物，不是扩展失效。** 把两个数摆到**同一操作点**上比：
- **每卡 64 在飞**：2 实例 22.392 vs 2 × 单实例 11.103 = 22.207 → **100.8%**（几乎满线性）
- **每卡 128 在飞**：2 实例 25.297（EXP-025 实测）vs 2 × 单实例 13.049 = 26.098 → **96.9%**

而 EXP-023/024 的 `20.87 / 12.807 = 1.63×` 是这么来的：**分子**是 replica2 在**客户端 conc128** 下的吞吐——经代理均分后**每卡只有 64 在飞**（→ 每卡 10.44 req/s）；**分母**是 colocate 在**客户端 conc128** 下的吞吐——**单卡 128 在飞**（→ 每卡 12.807 req/s）。**两个不同的并发操作点被放在同一个比值里**，于是"扩展效率"被算术压低了。

**【推断】④ 正确的说法**：`replica2` 与 `colocate` 的对比必须声明**每 GPU 在飞量**；在匹配的操作点上，**第二张卡带来 97–101% 的线性加成，没有可测的主机级干扰**（本实验在每卡 64 在飞处直接量到 100.8%）。这也解释了为什么 EXP-027 能在代理层只找到 2% 的损耗——缺口本来就不在"转发"或"主机争用"上，而在**口径**。

**【实测】⑤ S2 与 S3 分离了"请求量"与"并发"**：两者都是 N=1200，`conc64 → conc128` 使吞吐 11.103 → 13.049（**+17.5%**），代价是 TPOT p50 38.97 → 69.61 ms（**+79%**，已破 50 ms SLO）、TTFT p99 2.82 → 6.12 s。**即：单实例在 conc64 就已接近其吞吐平台，再加并发主要是拿延迟换一点点吞吐。** 这与 EXP-024 发现的"tp2 在 conc64 即饱和"同源——**在本机的这套 workload 下，单卡 conc64 是个自然的操作点**，而 `colocate@conc128 = 12.807` 是刻意压到过饱和的对照点。

**【推断】⑥ 对整体结论的影响**：EXP-024「replica2 全桶最高」的**排序不变**（22.39 > 12.81 > 12.30 > 8.15），但**「512 桶扩展效率 1.63×」这个数字与它的解释要改**——它不是「扩展失败/受互联与主机拖累」的证据，而是**两个不同并发操作点相除**的结果。四臂在同一「每卡在飞量」下的公平重测**本实验没做**（只做了 replica2 与 colocate 两臂），登记为开放项（§7）。

## 7. 异常、偏差与开放问题

- **协议**：三臂同栈、同 seed（1099）、同 workload（512×128）、`--request-rate inf`；两实例全程在跑，8200 空转；代理未使用（离了代理这一层，本实验只问"单实例承载力"）。未偏离预注册判据。
- **装置校验是本次最强的一环**：S1 与 EXP-027 A1 的 0.04% 吻合不是运气——两者都是"单实例、N=600、conc64、直连 :8100"，说明两次起栈的实例性能高度可复现（跨小时的 fresh 栈）。这为"跨记录比较"提供了依据。
- **口径混用已在 §6③ 显式指出**：本记录自身也用了两种口径（同 N 的 1.716×、同每卡在飞量的 100.8%/96.9%），凡引用必须带口径。**最容易犯的错是把 1.716× 当成"扩展效率"**——它同样混了操作点（单实例 128 在飞 vs 两实例各 64 在飞）。
- **未做（明确挂账）**：① **四臂在同一每卡在飞量下的公平重测**（本实验只覆盖 replica2 与 colocate；tp2/pd1p1d 未做，而 tp2 是单实例形态、pd1p1d 天生两实例，两者的"每卡在飞量"定义还需先想清楚）；② 每卡 128 在飞时的 **2 实例实测**（本次只有 EXP-025 的 conc256 单点，且经代理）；③ 主机侧未做 CPU/PCIe 计数，所以"没有主机级干扰"是**从吞吐差推出的**，不是直接观测。
- **一处措辞自查**：S2 的 TPOT p50 69.61 ms 已超 SLO 50 ms，故 S2 只应作为"单实例承压上限"的读数，**不可作为推荐配置**（与 EXP-025 对 conc192/256 的处置一致）。
- 无 OOM、无端口冲突、无失败请求；时间盒实际约 6 分钟（起栈 ~70 s + 三臂各 ~50–110 s）。

## 8. 下游影响

- **EXP-024 §6⑥ 与 §8 的措辞须改**：`512 桶扩展效率 1.63×` → 应写成「**同每卡在飞量下 97–101%**（EXP-029 实测 100.8% @每卡 64 在飞、96.9% @每卡 128），`1.63×` 是不同并发操作点相除的产物」。
- **EXP-023 §6③ 的"256 桶后仍未封顶"** 与本记录互补：单实例在 conc64 附近即近平台，replica2 因有两卡才继续线性上升。
- **TECH_DOC §3.1 与 C11** 涉及"1.63×"与"扩展效率"的段落需同步口径；**面试口径**：被问"为什么 replica2 只有 1.63×"时，正解是"那是口径不对称；按每卡在飞量对齐是 97–101%，第二张卡几乎线性加成"——**这比原来的"受主机资源限制"更硬**，因为它有同操作点的直接实测（100.8%）。
- **新增可复用证据**：单实例 @ 512×128 的 conc64→128 交换曲线（11.10 → 13.05 req/s，代价 TPOT +79%）、单实例 N=600/1200 在 conc64 下几乎同吞吐（11.14 / 11.10，说明该点对 N 不敏感）。
- **红线**：本实验不进 `runs.jsonl`、不进 fig；`1.716×` / `100.8%` / `96.9%` 三个数都必须带口径引用，且不得与 EXP-007 的四臂饱和吞吐混用。
