# EXP-018 · NCCL allreduce size 扫描（补 EXP-002 小消息缺口 + 复测大消息带宽）

> **一句话结论**：无 P2P 下纯 NCCL allreduce 的延迟地板是 **~14µs**（decode 级 8 KiB 消息即此量级），大消息带宽平台 **~6.2 GB/s**——后者比 EXP-002《硬件三数》记录的 1.78 GB/s 高 3.5 倍，**「1.78 GB/s 带宽墙」在当前环境复现不了**，差异来源待查（§7）。

## 1. 目的与假设

EXP-002 用 `all_reduce_perf -b 1M -e 512M` 只测了大消息区间（1MB–512MB），得「avg bus bw 1.78 GB/s」。两个缺口：

1. **decode 级小消息（8 KiB）没测**。llm-engine#EXP-D22 反推「88µs/次小消息延迟地板」，但这个数是含 torch.distributed Python 调度 + 双进程同步的完整开销，**纯 NCCL allreduce 的延迟是多少没有实测**。
2. **大消息带宽只有一个单点区间**，且 1.78 GB/s 与裸拷贝 22.7 GB/s（同次测量）差 12 倍，比例存疑。

假设：小消息存在一个 ~15µs 量级的延迟地板（与 EXP-002 的 GPU 间延迟 14.5–15.9µs 同阶）；大消息带宽应显著高于 1.78 GB/s。

## 2. 环境与配置

- 工具：`/root/tools/nccl-tests/build/all_reduce_perf`（tool_sha 717b683182，与 EXP-002 同一二进制）。
- NCCL：**显式 `LD_LIBRARY_PATH` 指向 v0.25.1 venv 的 libnccl.so.2.28.9**——本机 `/lib/x86_64-linux-gnu/libnccl.so.2` 是系统全局 2.25.1，裸跑会静默落到 2.25.1 造成版本漂移（铁律 8 精神：环境差异必须显式而非静默）。
- 参数：小消息区间 `-b 8 -e 1M -f 2 -g 2 -n 100`（n=100，小消息噪声大）；大消息区间 `-b 1M -e 512M -f 2 -g 2 -n 20`（与 EXP-002 同参数，可复现核对）。
- PCIe：空闲 Gen1（省电降频），allreduce 运行期间实测升到 **Gen4 x16**。

## 6. 分析与结论

**① 延迟地板 ~14µs，decode 8 KiB 消息即此量级。** 16B–8K 区间 time 稳定在 13.5–14.2µs（8B 的 17µs 是极小子消息的测量噪声），8 KiB 消息 13.79µs。这个地板与 EXP-002 的 GPU 间延迟（14.5–15.9µs）同阶——无 P2P 下 SHM 通路的小消息延迟 = 互联延迟地板本身。

**② 与 llm-engine#EXP-D22 的「88µs/次」对账：纯 NCCL 传输 ~14µs，其余 ~74µs 是 torch.distributed 的 Python 调度 + 双进程同步 + 漂移吸收。** EXP-D22 的 88µs 是从「8B 通信占比 10%（4.9ms/tok，56 次）」反推的完整开销，现在有了纯传输的实测锚（14µs），把「传输」和「调度/同步」拆开了——这强化了 EXP-D22 的「派发主导」归因：decode 通信里真正搬数据只占 14/88 ≈ 1/6，其余是同步等待。

**③ 大消息带宽 6.2 GB/s，EXP-002 的 1.78 GB/s 复现不了（差 3.5 倍）。** 同二进制、同 NCCL 2.28.9、同参数、同 driver、同硬件，1M 消息从 EXP-002 的 600µs/1.75 GB/s 变成现在的 192µs/5.45 GB/s，整个大消息区间稳定在 6+ GB/s。这不是噪声，是系统性差异。可能原因：EXP-002 测量时（8/21 15:06Z，恰逢 B1 矩阵战役同日）系统/GPU 有并发负载，或当时 PCIe 未升到 Gen4——EXP-002 的 provenance 未记录 PCIe 运行态，无法回溯判定。

**④ 带宽拐点结构。** 延迟主导区（<16K，~14µs 恒定）→ 过渡区（16K–256K，带宽 1.2→3.0 GB/s）→ 带宽主导平台（≥512K，6+ GB/s）。decode 落在延迟主导区，prefill（512 token × 4096 hidden × 2B = 4 MiB）落在过渡区末端/平台边缘——**TP 的通信成本在两阶段完全不同**：decode 付延迟地板，prefill 付带宽。

## 7. 异常、偏差与开放问题

- **核心开放问题：EXP-002 的 1.78 GB/s 为什么复现不了？** 候选：8/21 并发负载 / PCIe 未升 Gen4 / 其他环境态。EXP-002 的 all_reduce_perf.txt provenance 未记录 PCIe 运行态与系统负载，无法回溯归因。**本次不武断追认 EXP-002 为「测错」**，只登记差异；是否把硬件三数的权威数字从 1.78 更新为 6.2、以及是否连带修订 EXP-005 的「prefill 零加速归因」与 RESUME_EVIDENCE 的「1.78GB/s 带宽墙」措辞，留待用户决策（涉及多处下游结论，属「主张有据」与「单一事实源」的权衡）。
- 运行间 1M 点有 ±0.7 GB/s 抖动（4.73/5.11/5.45 三次），来自 PCIe 升频时机与 CPU 缓存态，量级一致、不影响平台结论；若进对外数字建议按「大消息平台 ≥6 GB/s」报区间。
- 只测了 float/sum 一种 type+redop，未测 half（decode 实际是 bf16）——allreduce 对 dtype 不敏感（字节数相同），但未实测，标注。
